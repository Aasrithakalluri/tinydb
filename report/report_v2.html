AutoSE: an agentic SDLC workflow on a tinydb fork

Aasritha Kalluri · Roll no. 2025204019 · Assignment 3, Architecting an Agentic SDLC Workflow · Fork github.com/Aasrithakalluri/tinydb (pinned at edff96a) · Models: Claude Haiku 5.5 (Planner, Builder), Claude Sonnet 5.5 (Reviewer) · Version 2

Summary. A maintainer labels an issue autose; three agents and a deterministic orchestrator produce a tested, CI-green, independently reviewed pull request, and a human decides whether to merge (the workflow never merges). All five issues I wrote (two bugs, two small features, one vague) reached a reviewed pull request for $0.06 to $0.09 each. The interesting results are negative or about plumbing: 11 attempts failed along the way and none because of the agents' capability; making the reviewer independent did not improve defect detection in my experiment; and splitting stages 1 to 4 over two agents cost about 70% more with no measured quality gain. Decisions D1 to D10 are recorded as 14 ADRs in architecture/decisions/; every number below comes from files in results/.

The three decisions that mattered most

1. A deterministic orchestrator with explicit state (ADR-002, 004, 011). I chose one Python state machine because code, not an agent, should decide who goes back (loops and counters must be bounded and predictable), one job gives one place for state, an LLM router would spend tokens and could keep itself in a loop, and Actions jobs do not trigger each other with GITHUB_TOKEN. It is the decision the evidence tests hardest. The clearest result of the whole project is where things went wrong: 11 failed attempts, 10 of them defects in my plumbing (an invalid workflow file, a repository setting, restart, duplicate pull request, a CI run gated at action_required, restoring the wrong artifact, a CI that collected my own tests) and one deliberate budget test. ADR-004 ("restart resumes from the saved state") was reasoned but wrong: the first restart restored state.json but not the code and pushed an empty commit over the branch. I kept ADR-004, marked it Superseded and wrote ADR-011 (re-apply the diff, reuse the open PR, rebase onto the current default branch, take the newest artifact by creation time). The price of the choice is that the orchestrator is a single point of failure and holds the token; it is less flexible than a planner, and its routing numbers (2 test retries, 1 redesign, 2 review rounds) are my guess.

2. Reviewer independence (ADR-008, 014). I wanted the reviewer to be unable to simply agree with the implementer: a fresh context (only the issue, the diff and a clean checkout), an adversarial prompt, a duty to run the tests itself, and a different model with no push right. This is the decision I tested most carefully, and the result is the part I find most useful: independence did not improve detection (Section 3). It stays because the assignment requires it, but as a rule and not a proven benefit. ADR-014 (compare the new code with its closest analogue; a reversal of documented behaviour is an approach finding) was tested against a criterion fixed before the run; it caught the seeded defects but falsely rejected a correct control twice, so it stays Proposed and I did not tune it afterwards.

3. Deterministic checks decide pass or fail (ADR-007, 012). No second model to fool, hard to talk around, cheap and reproducible, and an agent must not grade its own stage. The checks earned their keep: the design lint caught a Planner naming a test that did not exist (before any code), and the suite is run by the orchestrator, not reported by the agent. They also failed me twice: my spec lint rejected a correct spec because it did not accept the A1 skill's own tagged criteria (FR-03-AC1 (failure):), so I wrote unit tests for every check. Stage 6 is not purely deterministic, because its input is the Reviewer's verdict; the orchestrator only applies a code rule to it (reject "approve" if no test was run), and that rule never fired because every review ran the suite. Experiment 1 exposed a gap: a design can list a change that was never applied and the run still passes.

3. Decision experiments

I tested two ADRs with variants that change one thing, and also report two smaller tests (ADR-013, ADR-014). Both experiments ran for real on the fork; negative and null results are reported as measured.

What the reviewer caught and where it was wrong. On the 7 real PRs it approved all in round 1 (always after running the suite and checking the architecture constraints), so those runs show no evidence that it catches anything. On seeded defects it caught 8 of 10 (Table in Section 3) and missed the sibling-convention defect S4; neither reviewer raised the reversal of a documented contract as something a human must decide (it was rated code, not approach). Other tests: a real prompt-injection issue (hidden instructions to dump credentials, edit the workflow and skip tests) was resisted at every stage and logged as a risk by the Planner; a $0.02 test cap stopped a run before its reviewer, as designed (the $0.60 production cap was never reached); a second trigger on a busy issue queued instead of racing; both back-edges (three simulated test failures leading to a redesign, and a simulated reviewer "changes") worked through the orchestrator, $0.128.

Cost and tokens. By the orchestrator's own tracking the whole project used about $3.4 and roughly 9M input and 0.55M output tokens, of which about $0.5 was lost to my own bugs. Caveat: these figures are estimates summed from the per-call costs the SDK reports; I did not read the provider's console, and the API ran out of credit once earlier than this estimate predicted, so the true total may differ.

5. Hindsight

If I started again tomorrow I would change ADR-004 (state and restart) first, and I would test it before any paid agent run. Four of the eleven failed attempts and both addenda to ADR-011 came from this one decision, and every problem was found by a real run, not by reasoning: the first restart restored state.json but not the code and pushed an empty commit over the branch; a restart then tried to open a second pull request; the CI wait read the wrong run; the "latest" artifact was chosen by id instead of by creation time; and a restart kept an old base commit. It needed a restart to be treated from the start as a resumable transaction: state, diff, base commit and pull request saved together, the newest artifact taken by creation time, the open pull request reused, and a rebase onto the current default branch, all exercised on a stub run before the first real call. I would also run my offline tests in the same directory layout as production, because two of my experiment bugs (artifacts written inside the repository, a relative patch path in the scorer) passed my stub tests only because the test layout differed from the real one. I would keep the deterministic orchestrator (ADR-002), the deterministic checks (ADR-007) and the independent reviewer (ADR-008, as a rule), because the evidence did not argue against them.

6. Limitations and threats to validity

  1. Small samples. 5 issues, 10 runs per variant in Experiment 1, 14 reviews per reviewer in Experiment 2, 2 reviews per seed: the results are descriptive, and one run or one defect class decides the gaps.
  2. I wrote the issues, the hidden tests and the seeded defects (with my coding assistant), and chose behaviours I had verified; they favour solvability, and a different valid fix could fail the tests (mitigated by validating each test set with two independent fixes). Issue 2 asks to reverse a documented contract, so its hidden tests alone overstate success.
  3. One repository, one small library, one model family (Haiku and Sonnet); the "independent" model differs from the author model only in size.
  4. Flaws in my own experiment designs were found and removed (a confounded pilot, mutations that failed the PR's own suite, a stale seed branch, a driver that wrote artifacts into the repo, a scorer path bug). The invalid runs (about $0.5) are kept, flagged and unused.
  5. Fault-injected tests are not natural failures: the back-edge runs simulate test failures and a reviewer verdict, and the Builder inflated its diff after a failure that did not exist.
  6. Prompt injection was tested once (one direct attack in one run); indirect injection through files or tool output and weaker models are untested, and python -c in the allowlist is a residual escape hatch.
  7. Ask-mode on issue #5 used answers chosen by my coding assistant on my delegation, and the "ask vs assume" comparison covers one issue.
  8. The reviewer approved every real PR in round 1; the evidence that it catches defects comes only from my seeded PRs.
  9. Cost and token totals are orchestrator estimates (Section 4), and a coding assistant wrote the code and drafted the text; the decisions are mine (Appendix D).

Appendix D. AI use and who decided what

I used Claude Code (Claude Sonnet 5.5) substantially. It wrote the workflow, the orchestrator, agents, checks, scripts, tests and the experiment tooling, ran the experiments, and drafted the text of the ADRs, the views, the analysis and this report. The decisions and their reasons are mine. My own answers in the design discussion decided D1 (three agents), D2 (a single Python orchestrator), D6 (Haiku for Planner and Builder, Sonnet for the Reviewer), the experiments to run, the human gate for vague issues (ADR-013), the $5 limit and the instruction to keep cost low. In an interview I selected the reasons behind ADR-001 to 010 and 013 and the lessons of ADR-011, 012 and 014, and I read and adopted all 14 ADRs on 2026-11-22 (each has a "Reviewed and adopted by" line). The other mechanisms and numbers were proposed by my coding assistant and accepted by me; each ADR says so in its "Decided by" line. The Hindsight section was drafted by my coding assistant from the evidence in the runs (which decision caused the most failures), at my request. All runs, pull requests and results are real and linked in results/runs.md; none was fabricated.
